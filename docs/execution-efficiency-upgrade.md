# 执行效率升级：pure 做复杂任务为什么慢，怎么治

2026-10-10 诊断。用户实测三个症状：复杂/多步任务异常耗时；测试环节反复跑全量
e2e；决策点上反复权衡迟迟定不下来。多 agent 并行没有兑现成速度——「我做多
agent 的目的之一就是并行加速，实际体验却是异常漫长」。

本文是病灶清单（全部带代码位置，逐条核实过）+ 改造刀。总原则延续
2026-10-10 停支重构的定调：**涉及理解的判断归模型，宿主只做机械执行**；
时间预算、缓存、并发池是宿主基础设施，可以硬；「跑哪些测试」「要不要重
规划」是理解，必须模型判。

## 一、病灶：三类结构，不是单点低效

### A 类：验证环节的全量重复执行（wall time 最大头）

| # | 病灶 | 位置 | 量级 |
|---|------|------|------|
| A1 | 回合末交付门禁：typecheck→lint→test→build 按整体脚本全量串行，无「受影响」选择，每步上限 180s | chat.ts:6086-6145、delivery.ts:497-543（DELIVERY_STEP_TIMEOUT_MS:431） | 每个构建回合 4 步 × 数十秒~3 分钟 |
| A2 | 模型回合内自跑同一套管线，且规则写死「任何一步失败：从失败步重新执行，循环直到全部通过」；回合末宿主 backstop 再全量重跑一遍 | delivery.ts:381-410（formatDeliveryPipeline 注入 user turn，chat.ts:5449）、chat.ts:6103 | 每回合全量至少两遍，失败循环无上界 |
| A3 | 门禁失败 → 最多 3 轮修复，每轮 = 一整轮 LLM 修复回合 + **从头**重跑全部验证步骤（不管哪步失败都从 typecheck 开始） | chat.ts:6068（MAX_QUALITY_REPAIR_ROUNDS）、6111-6128、5219-5270；CLI 同构 cliRepl.ts:574-605 | 每轮修复 = LLM 回合 + 4 步全量 |
| A4 | auto-continue 最多 20 轮，每轮 auto 回合末再跑一次全量门禁（+可能的 3 轮修复）；每轮重新 discoverWorkspace（递归 list_files 全工作区，无缓存） | autoContinue.ts:16、chat.ts:7079-7090、requestWorkflow.ts:95-100、chat.ts:4650、delivery.ts:198-248 | 长任务 = 最多 20 ×（LLM 多轮 + 4 步验证 + 3 轮修复） |
| A5 | 瞬时失败单步重跑 ×2，叠加 180s 工具硬超时 | delivery.ts:482-495、ToolExecutionCoordinator.ts:16 | 最坏一轮门禁 ≈ 4×(180s×2) ≈ 24 分钟 |

**这就是「测试环节反复跑全量 e2e」的完整机制**：不是模型笨，是宿主的门禁
结构强制每次都付全价——模型自跑一遍（A2）、宿主复查一遍（A1）、失败推倒
重来（A3）、auto-continue 每轮再来（A4）。

## 二、业界对照（2025-2026）

- **测试**：Nx/Turborepo 的 affected-only（按 diff+依赖图只跑受影响子集）已成
  monorepo 标配；fail-fast 分层反馈环（typecheck 秒级 → 相关单测十秒级 → 受
  影响集成 → 全量 e2e 只在合并/收尾跑一次）是 agent 编码环的公认实践；
  全量回归反复跑被视为反模式。
- **决策**：plan-once-execute-many——执行期锁计划，仅现实偏离才重规划，且只
  重排受影响部分（checkpoint 续跑，Recoverable Execution for Long-Horizon
  Agents, arXiv 2026-08）；Explore→Plan→确认后执行（Anthropic 官方工作流）；
  给权衡设预算（budgeted deliberation）；可回滚操作先斩后奏。
- **并行**：subagent=独立上下文+独立 LLM 会话（Claude Code、Anthropic 研究
  系统）；谁完成谁收执、汇合不设屏障（反例：LangGraph super-step 屏障被
  官方确认为减速带）；Anthropic 自认多 agent 是 15×token 换 90.2% 质量；
  arXiv 2601.12307 证明同构多 agent 的增益多为缓存假象——**并行只在子任务
  真独立时兑现，否则多 agent=加延迟加成本**（Cognition《Don't Build
  Multi-Agents》同结论）。
- **调用**：prompt caching（稳定前缀打断点，缓存读约 1 折价 + TTFT 显著降）；
  小模型分流（简单判断走轻模型）；流式提前决策（不等完整回复）；每轮重建
  上下文 = 缓存全 miss 是最被低估的反模式。

## 三、改造刀（按预期收益排序）

### 刀 1：验证增量化——受影响面由模型判，宿主只执行（对准 A 类）

1. **验证计划进模型之手**：计划阶段（planByThinking 产出计划时）让模型按
   本轮改动面一并产出「验证清单」——要跑哪些命令、为什么够。宿主把清单当
   参数执行，不再无脑跑整体脚本。模型没给清单 → 退回现状全量（保守兜底）。
   全量 test/build 只在任务**收尾**跑一次，迭代环内只跑清单上的。
2. **修复轮只重跑失败步**：A3 的「从头重跑全部」改为只重跑上轮失败的步骤
   （delivery 已有步级结构，改执行顺序即可）。
3. **模型自跑管线与宿主 backstop 合并**：A2 的双份全量砍成一份——宿主
   backstop 保留（机械兜底），模型回合内的自跑循环改为「跑到清单上的最小
   集通过即可」。
4. **discoverWorkspace 会话内缓存**：mtime/条数不变直接复用（机械缓存，
   不涉判断）。
5. **门禁步超时分档**：typecheck/lint 不该与 test/build 共享 180s。

预期：长构建任务的验证 wall time 从「每回合两遍全量 × 最多 20 轮」降到
「每回合增量一遍 + 收尾一次全量」。

### 刀 2：拆汇合屏障——谁完成谁收执（对准 B 类）

1. **提示词改口**：promptLayers.ts:394 的「every call has returned」改为
   「已返回的先并、慢支回来后补并；慢支超时给出部分产出也算数」——把「等
   全齐」从模型义务里拿掉。
2. **折入与汇总解除全齐闸**：foldInLedger/chat.ts:1675 的 in-flight 判定从
   「全部收齐」改为「按支结算」——一支结算即可入账/入汇总草稿。
3. **父 THINK 中途边界**：runBatch 逐支结算时允许父在「已有 ≥1 支完成」时
   先做一轮轻 THINK（整理已到手的），不再硬等到整批完。（宿主机制，不替
   模型判断——何时并、并什么仍是模型的事。）
4. **单支预算降档 + 慢支部分产出**：30 分钟单支超时降为可配置的合理档；
   超时/看门狗触发时收集已产出部分入账，标明「此支未完，部分产出」——由
   汇总模型决定够不够用，而不是全树白等。
5. **provider 排队缓解**：子支 LLM 适配器与父分离（至少裁决器/插话链先分
   出去——它们已经在独立档位 judgeLlm 上），并发池上限按 provider 实际
   配额走配置而非写死 5。

### 刀 3：决策预算——「反复权衡」的三刀（对准 C 类）

1. **思考窗重想改攒批**：C2 的 N 句补充 N 次重想改为「窗内插话攒批，一次
   重想带上全部」——机械合并（宿主拼接），判断仍归模型一次做。
2. **路由降延迟**：6-12s 语义路由与规划思考并行开跑（路由只影响入口编排，
   不依赖规划产出）；同会话同话题命中上轮路由结果直接复用（缓存，不判断）。
3. **规划思考收口**：180s 满窗等待改为「计划成形即收」（模型流式给出结构
   化计划段即提前结束），剩余思考并入执行首 THINK。
4. **插话裁决合并**：同回合多条插话合并一次裁决（chain 串行 → 批量）；
   低置信追问保留，但追问答案与原句合并重裁而不是重走全链。
5. **压缩移出阻塞路径**：C4 的摘要改后台预取（接近阈值就开始备摘要，驱逐
   时直接换入）。

### 刀 4：调用效率——缓存与分流（对准 B4/C5 边际成本）

1. prompt caching：系统提示词/工具定义/花名册骨架等稳定前缀固化，易变内容
   一律追加在末尾——buildInsertionContext 现在每次现场重排，需改成「稳定段
   在前不动 + 变化段在后」。
2. 小模型分流：插话分类/聚焦点名/路由这类「判断但轻」的调用走轻模型档
   （档位机制已有，接轻模型即可）；编写/规划/汇总留主模型。
3. auto-continue 与 guard 的推力合并评估：C5 三层各付整回合，改为统一预算
   计数器（机械），并把「要不要继续」的判断明确交给模型在收尾 THINK 里
   一次表态。

## 四、验收口径

- 同一个复杂构建任务（用户实测的那类）：总 wall time 与 LLM 调用次数前后
  对比；「全量 test 运行次数」应从 O(回合数×2+修复轮) 降到 O(1~2)。
- 多支并行任务：最快支结算到第一份产出入账的延迟（应从「整批收齐」降到
  「首支完成」）；单支挂死时全树最长等待（应从 30 分钟降到降档后的配置值）。
- 插话体感：从插话到宿主首次响应的延迟；连续补充场景的重想次数（N 次 → 1 次）。

## 五、不做的事

- 不给宿主加「智能」默认值：测试选不选、继续不继续、并不并入账——宿主只
  提供机制（缓存、预算、并发池、屏障解除），判断一律模型。
- 不动插话协议的判定语义（裁决器主权），只动它的延迟与串行结构。
- 不做激进全路由（小模型包揽）：误路由的返工比省下的钱贵，只分「轻判断」档。

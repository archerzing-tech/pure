# 远程会话观察与指挥（手机经通道看桌面业务）——设计稿

2026-11-08 · 状态：设计定稿待评审，未开工。

## 一句话定调

桌面跑业务，手机当遥控器：**本地执行、远程观察、远程指挥**——不新做 app，已有五通道（Telegram / QQ / 飞书 / 钉钉 / webchat）的手机端就是客户端。

## 设计锚场景（用户 2026-11-08 定调）

1. **卡住解救**：桌面端某任务被卡住无法执行 → 手机发指令让这个会话继续。
2. **中途改向**：看到某任务的结果不是想要的 → 手机发命令让任务改变执行方向。
3. **进度查问**：可能只是想看看桌面端某个会话运行到哪一步了——不一定要干预，也不一定想被持续推送打扰。
4. **远程启动**：直接从手机启动一个新项目/新会话开跑，不依赖人在电脑前。

前两个场景的共同点：**指挥是主诉求，观察只是前提**——先在手机上看到「卡在哪/产出了什么」，才谈得上发指令。设计重心因此从「远程观察」调整为「观察+干预并重」，指挥面提前进 P1，审批镜像提前进 P2。第三个场景是独立的高频轻场景，催生**分层访问**：瞄一眼零负担，重的操作才留痕。

「卡住」不是一种状态，是四种，各有解法：

| 卡住形态 | 手机上看到的 | 解法 |
| --- | --- | --- |
| 卡在授权弹卡 | `⏸ 等待授权：execute_command · rm -rf …`（超 30s 未决升级为告警推送） | P2：`/approve` / `/reject` 直接清卡；P1 过渡：`/stop` 后发「换个方式做」 |
| 流挂死/超时 | `⏸ 回合无输出已 120s` | `/resume`——触发与桌面端超时恢复同一套现场注入续跑（P2） |
| 止损停（auth 失败/重试烧尽） | `⛔ 回合止损：<原因>` | 直接发「继续」=新回合：失败账在会话上下文里，模型自然换路重试，**无需新机制** |
| agent 认为做完，人认为没做完 | `✓ 回合完成：<摘要>` | 发「还没做完，接着做 X」=新回合，同上 |

改向同理分两态：**跑动中**改向=插话（interject 协议改向/取消一部分 relation 自判）；**已落结果**不满意=新回合带反馈（上一回合产出就在上下文里，模型看到「不对，改成 X」自己修正）。

## 业界对照与本设计的差异

| 产品 | 形态 | 与 pure 的差异 |
| --- | --- | --- |
| Claude Code Remote Control（2026-02） | `claude remote-control` 显式开远程会话，Claude 手机 app/web 看会话列表+发消息+审批；**一次只能一个会话** | 要自家 app/web；pure 用通用 IM，天然多端多会话 |
| Cursor Cloud Agents | 云端跑（非本地），cursor.com/agents 手机浏览器监控；社区自发做 Discord 集成 | 云依赖；pure 本地跑零云端，社区自发造 IM 集成恰证明 IM 控制面是真需求 |
| OpenClaw 类 | 手机控制个人设备 | 通用设备控制；pure 聚焦「对话业务」这一种对象 |

三个业界教训（Remote Control 上线初期的坑，设计必须规避）：

1. **状态必须真话**：会话终止后手机端收神秘错误而非「会话已结束」——pure 的附着状态机必须把「桌面退出/会话删除/网关断开」如实推给手机。
2. **审批链路要独立可用**：弹卡悬着正是「卡住解救」场景的主要形态之一——pure 虽定调「确认弹卡尽量自动允许」（pure-priorities-intelligence-over-security），但悬着的卡必须能在手机上清掉，审批镜像放 P2 而非挂账。
3. **隐式开远程不可取**：Claude 要显式命令开远程会话；pure 的对应物是显式 `/attach`——**默认零推送**，附着才推，这是隐私默认线。

## 核心概念：附着（attach）

channel 对话（手机侧一个 chat）与桌面会话（pure session）之间的一条**有向订阅**：

```
手机 chat  ──attach──▶  桌面 session
   │                       │
   │  指令（消息/斜杠命令）  │  事件流（投影后）
   └───────────────────────┘
```

- **发现**：`/sessions` 列出桌面全部会话（标题/工作区/当前状态/最近活动，跑动中的标出当前步骤）。
- **附着**：`/attach 2`（或点列表卡片按钮）开始订阅该会话的投影事件流；`/detach` 停止。**附着即回填**：附着瞬间先推一份「最近投影」（最近回合完整 md+当前状态行）——否则附着到跑了一半的会话只能看到之后的增量，上下文缺失。不做「回复数字」快捷操作：附着状态下纯数字是插话内容，同一输入两种解释误触成本高，控制词一律写全。
- **观察面**（简略形态，见下节）实时推送到手机。
- **指挥面**：往手机 chat 里打字 = 给附着中的会话发指令（跑动中=插话，空闲=新回合）。
- 一个 chat 同一时间附着**一个**会话（切换即重新 attach）；一个会话可被多个 chat 同时附着（广播）。多对多留 P3。

三层访问，按需取用——瞄一眼零负担，盯着看才推送，要指挥才发指令：

| 层 | 动作 | 特征 |
| --- | --- | --- |
| **L0 查问** | `/sessions`（列表带状态）/ `/status <n>`（单会话进度快照） | 一次性回答，**不附着不推送**，用完即走 |
| **L1 附着** | `/attach <n>` … `/detach` | 持续订阅投影流（状态行+工具行+回合完成） |
| **L2 指挥** | 附着中打字发消息、`/stop` `/approve` `/resume` `/new` | 改变会话行为或创建会话 |

## 简略形态：投影规则（用户定调：纯文字+md，其余不支持）

复用既有 formProjections / textFallback 机制（三方同源锁已在），新增「通道投影器」：

| 桌面形态 | 手机投影 |
| --- | --- |
| assistant 正文 | md 原文（通道支持什么发什么，不做通道特化富卡——第一版纯文本下限） |
| 工具调用 | 一行摘要：`🔧 execute_command · git status · 3.2s ✓`（名称+一句话参数摘要+耗时+成败） |
| 思考过程 | 默认不推（刷屏）；`/think on` 可开，开也只推缩略 |
| 图表 / 地图 / PPT 卡 / 交互卡 | 占位行：`[图表：月度销售 — 桌面端查看]`（名称取卡标题） |
| 生成图片 | 不推图（IM 图床/压缩不可控），占位行同上 |
| 授权请求 | 状态行 `⏸ 等待授权：<工具·参数摘要>`（这是发现「卡住」的主要眼睛）；卡按钮镜像 P2 |
| 回合状态变化 | 状态行：`▶ 开始` / `⏸ 等待授权：<卡名>` / `✓ 完成+摘要` / `⛔ 失败+原因` / `⏹ 已停止`——其中**等待授权超 30s、失败、止损停**三类升级为告警推送，附着的 chat 一定收到（遥控器的意义就是不必守在电脑前） |
| 流式输出 | **不逐 delta 推**——按回合粒度推：回合结束推一次完整 md；长回合（>60s）中途每 30s 推一次「进度快照」（当前工具+已产文本尾部 200 字） |

投影纪律三条：

1. **参数值不过账**（与错误台账同一纪律）：工具摘要里的参数只给安全摘要（文件路径/命令前 60 字符），凭据类参数（configure_channel 等）只出工具名。
2. **降级可读**：投影失败（卡无标题、异常形态）回退成 `[未识别内容块]` 占位，不静默丢。
3. **洪控**：单会话事件密度超阈值（如 1 分钟 >30 条投影）时合并成摘要行，手机端永远不被刷屏炸群。

`/status <n>` 进度快照（L0 拉取，未附着也能查）：

```
会话 2 · 重构错误台账 · 跑动中
▶ 第 4 步：execute_command · cargo test --lib（运行中，已 45s）
✓ 已完成 3 步：read_file ×2、git status
尾部输出：「…测试全部通过后提交」
```

空闲会话返回最近回合摘要+最后活动时间。数据源与投影流同源（GUI 侧同一状态），只是拉取而非订阅。

## 指挥面：插话语义的通道映射

pure 独有的插话协议是这套设计最有价值的部分——手机发的不只是「新消息」，是完整的控制语义：

| 手机动作 | 桌面会话状态 | 语义 | 走既有机制 |
| --- | --- | --- | --- |
| 发消息 | 空闲 | 新回合输入 | 等同桌面输入框发送 |
| 发消息 | 跑动中 | 插话 | interject 协议九类 relation 自判（补充/改向/取消一部分…） |
| `/stop` | 跑动中 | 停止 | Esc 统一语义（先暂停再硬停） |
| `/approve` `/reject` | 有悬着的授权卡 | 弹卡决策 | 与桌面点按钮同一落点（P2） |
| `/resume` | 流挂死 | 现场注入续跑 | 与桌面超时恢复同一机制，手动触发（P2） |
| `/new [目录]` | 任意 | 新建会话 | 网关 invoke GUI 创建（GUI 是会话真身）；**创建即附着**——从手机建的会话用户必然要盯它；目录可省略（用上次会话工作区），桌面侧栏如实出现新会话（P2） |
| `/plan` | 任意 | 查看当前计划 | request_plan 状态 |
| `/status` | 任意 | 会话快照 | 最近回合+工具计数+耗时 |

## 架构（侦察修正版，2026-11-08）

**关键架构事实（代码侦察确认）**：通道网关不是 Rust，是**独立 Bun 守护进程 `pure gateway`**（TS，`src/cliChannels.ts`，Rust 壳只 spawn/探活）；GUI 与网关今天零通信，只共享 `~/.pure` 磁盘。会话真身（引擎+插话协议+投影器）全在 GUI WebView。

```
手机 IM ←→ 通道网关（Bun/TS 独立进程，src/channels/*）
             │  适配器 send/editMessage + SessionRouter + attach 注册表（新）
             │  Bun.serve 已存在（webchat），新增 127.0.0.1 内部 WS 端点
             ▼
         localhost WebSocket（新缝，双向）
             ▲
           GUI WebView（src/ui/remoteBridge.ts 新建 WS client）
             │  投影缝挂 chat.ts 引擎事件消费点（ToolStarted/ToolResult/
             │  StateChange/Completed/Interrupted/Error）
             │  指挥落点 = ChatController.interject()（唯一入口，
             │  空闲自动 send 新回合/跑动自动裁决链——现成分流）
             │  /stop = pause()（第一段），再 /stop = cancel()（硬停）
             └─ Rust 壳基本不动（离线列表读 index.json 的 load_session_list 现成）
```

关键决策：

1. **附着注册表住网关进程**（`src/channels/attach.ts` 新建，持久化 `~/.pure/channels/attach.json`），chatKey（channelId:accountId:peerKind:peerId）→ sessionId 有向映射。网关重启从盘恢复。
2. **GUI↔网关缝 = localhost WebSocket**：网关在既有 Bun.serve 上加内部升级端点；GUI 新建 `remoteBridge.ts` WS client（自动重连）。协议四类：GUI→网关 `hello`（live 会话状态+当前步骤）、`projection`（投影文本）；网关→GUI `inject`（指挥文本，带 msgId 幂等键防多窗口重复处理）、`stop`、`query_status`（/status 在线查询）、`query_backfill`（附着回填）。
3. **投影住 GUI 侧**（看得见卡上下文），正文块复用 `richOutput.renderRichOutput` 纯文本降级链（图表→ASCII 投影+「完整源码见桌面端」note，现成）；状态行/工具行由投影薄层从引擎事件生成（ToolStarted/ToolResult 含名称/参数/耗时/成败，字段现成）。
4. **指挥注入单点**：网关 `inject` 消息最终落 `ChatController.interject(text)`——该函数内部 isStreaming 分流就是「空闲=新回合/跑动=插话」语义本身，无需新机制。`/stop` 落 `pause()`，paused 态再收 `/stop` 落 `cancel()`（与桌面 escapeWhileStreaming 两段式同构）。
5. **控制词在网关 routeInbound 门禁后识别**：`/sessions` `/status` `/attach` `/detach` `/stop`；未附着 chat 的普通消息走原路由零破坏。`/sessions` 数据源=`listSessionViews`（sessionViews.ts 现成，通道索引∪GUI 会话∪状态推导）∪ WS hello 的 GUI live 状态合并。
6. **入站路由**：chat 有附着时消息进被附着会话（不再走 channel 默认会话）；`/detach` 后恢复。channel 自有会话与附着会话互不污染，不附着时一切照旧。
7. **状态真话**：GUI 离线=WS 断开，网关对附着 chat 如实推「桌面已离线，推送挂起」；会话删除同。`/status` 离线时从磁盘 session.json/events.jsonl 出最近回合摘要（`readSessionTimeline` 现成）。

### 手机端如何「看到」桌面会话（发现链路）

手机 IM 只是个聊天窗口，它不直接连桌面——**通道网关（Bun 守护进程）常驻长轮询/长连接 IM 服务器**，这条链路现在就存在（通道对话走的就是它），`/sessions` 只是同链路多走一步：

```
手机 QQ 发「/sessions」→ 腾讯服务器 → pure 网关轮询收到
  → 识别控制词 → 组装列表（磁盘元数据 + GUI 运行状态）
  → 通道出站 → 手机 QQ 收到一条普通消息：

    pure 会话（3 个，1 个运行中）
    1. 重构错误台账 · ▶ 跑动中 · cargo test
    2. 周报整理 · 空闲 · 2 小时前
    3. 爬虫调研 · 空闲 · 昨天
    /status <编号> 看进度 · /attach <编号> 盯住看
```

列表数据两层来源：**磁盘元数据**（`~/.pure/sessions/<id>/session.json` 的标题/时间/模型——网关自己就能读，GUI 关了也能列，标「离线」）+ **GUI 运行状态**（回合开始/结束由 GUI 事件上报网关，「正在跑什么」只有引擎知道）。

## 分期（指挥前置重排）

- **P1 观察+指挥闭环**：`/sessions` + `/status`（L0 查问，未附着可用）+ `/attach` + 投影推送（回合粒度+状态行+告警+长回合进度快照）+ **发消息全语义**（空闲=新回合、跑动=插话——「改向」场景 P1 即闭环）+ `/stop` + 状态真话。
  验收=QQ 真机四条：①不附着直接 `/status` 拿到某跑动会话的当前步骤；②桌面跑带图表任务，手机看到文字+占位行+完成摘要；③跑动中手机发「方向不对，改成 X」，桌面气泡按插话协议呈现并改向；④止损停后手机发「继续」，agent 换路重跑。
- **P2 远程创建+卡住解救收口**：`/new [目录]`（创建即附着，手机一句「在 X 做个 Y」即远程开工）+ 审批镜像（`/approve` `/reject` + 告警卡直接按钮）+ `/resume` 续跑 + 快照节奏真机调优。
  验收=①手机 `/new` 后直接发任务，桌面新会话开跑、侧栏如实出现、投影流回手机；②人为造一张悬着的授权卡，手机收到告警推送，`/approve` 后桌面回合继续。
- **P3 多端与持久**：多 chat 附着一会话、持久订阅（重启恢复附着）、`/think` 开关。

## 风险与未决

1. **回合粒度推送的实时性取舍**：P1 不逐 delta 推（IM 速率限制+刷屏风险），长回合靠 30s 进度快照兜底——若真机体验「太钝」，P2 评估 10s 级快照。
2. **通道 md 方言**：Telegram/QQ/飞书对 md 支持参差——首期按各通道现有出站格式化能力（已解决的既有问题），不新增方言层。
3. **敏感会话**：内容出网到第三方 IM 与现在用通道对话语义等同，不做额外门（用户既有定调）；但 `/attach` 永远显式，永不默认推。
4. **会话列表的来源**：GUI 活着时以 GUI 为准（含跑动状态）；GUI 关闭时网关从磁盘 sessions 目录出列表（只读元数据，标「离线」）。
5. **GUI 不在场的新建**：`/new` 依赖 GUI（会话引擎真身），桌面关闭时如实拒绝。真正的「电脑关机也能开工」属于 headless 运行时议题（CLI 引擎无头跑回合），超出本设计边界，留作后续方向。

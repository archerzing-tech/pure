# 多子 Agent 暂停 / 续跑设计

状态：**方案定稿（2026-09-20），未实施**。起因：多个子 agent 并行跑着时用户点暂停，
现在等价于硬停——子 agent 被杀、进度作废、想继续只能靠模型碰运气重委派。用户期望：
暂停能停住子 agent，继续能接着跑；暂停后去做别的事了，这些子 agent 不用恢复。

## 一句话方案：暂停 = 存档，不是冻结

点击暂停时**不把运行中的东西冻在原地**，而是：手头这步安全收尾 → 全部落盘存档 →
干净地停下。点继续从存档原地接着跑，不重头再来；没人点继续，存档就静静躺着，绝不
自动复活。

### 为什么不做"真冻结"

1. **正在跑的工具没法冻**。装依赖的命令跑到一半：等它跑完，暂停延迟可能几分钟；
   杀掉它，白跑。两头不讨好。
2. **全内存状态抗不住崩溃**。App 一崩一重启全没；存档天然抗崩溃。
3. 要在引擎内部到处凿"闸门"，改动面大、测试面更大。

而存档方案的关键零件 pure 里已经全有，本质上是把三样现成机制串起来：

- **稳定 sessionId**：子 agent ID = `sub_<父会话>_<角色>_<任务哈希>`
  （`SubagentOrchestrator.ts` ~L399）——同样的任务再委派一次，路由到同一个存档；
- **checkpoint**：子 agent 中断时已把完整对话存进 stateStore（`subagent_interrupted`，
  ~L541）；
- **continue**：从存档续跑的入口已存在（`engine.continue({ messages })`，分段续跑
  机制天天在用）。

今天用户点停止，这套机制已经在跑——只是停完没人再触发续跑。**核心增量很小：把
"停止"分出"暂停"这个变体，再给暂停的东西一个「继续」按钮。**

## 具体机制

### 暂停时

1. 父回合与所有子 agent 收到带 `paused` 标记的中断信号（区别于现在 `cancelled` 的硬停）。
2. **正在执行的工具不杀**：等它跑完（各自超时兜底），结果照常存档——装了一半的依赖
   不白装。卡片显示"正在等当前工具收尾…"。
3. **LLM 流立即断**：推理到一半的内容没有保存价值，重发就是。checkpoint 以最后一个
   完整轮次为准（悬空 toolCalls 已有 `trimUnresolvedToolCalls` 修剪）。
4. 每个子 agent 卡片变"已暂停"态（`SubagentActivityEvent.kind` 增加
   `'paused' | 'resumed'`），父回合标记为暂停而非取消。
5. 输入框立即解锁，用户想干嘛干嘛。

### 继续时

1. 暂停卡片上出现「继续」按钮（浮动卡与对话内卡都有）。
2. 点击注入一个续跑回合：父 agent 从存档看到"我刚委派了 A、B、C 然后被暂停"，自然
   重新委派——**同样任务 → 稳定 sessionId 命中同一存档 → 子 agent 从断点接着跑**，
   不是重头做。这一步零新机制，是现成的"同任务再委派即续跑"语义。
3. 预算重新起算：墙钟重置（暂停时间不算），token 不退（历史都在消息里）。
4. **单飞保护**：有别的回合在流式输出时「继续」置灰——不允许两条执行流同时写一个会话。

### 用户走了不管（弃管）

存档是惰性的，没人点继续就永远不动。开全新任务，暂停卡片还挂着（可点继续，也可点
✕ 关掉——关掉时问一句"存档也一并丢弃？"）。副产品且合理：新任务恰好又委派了同一个
任务（如"刚才那个调研继续深入"），稳定 sessionId 自动接上旧存档——期望行为，非 bug。

## 边界情况

| 情形 | 行为 |
|---|---|
| 暂停时长命令正在跑 | 等收尾，结果存档；卡片显示等待态 |
| 暂停时某子 agent 恰好刚完成 | 完成态保持，不受影响 |
| 继续时有新回合在跑 | 「继续」置灰，等闲了再点 |
| 续跑后子 agent 接着失败 | 走现有 failurePolicy（重试→反思→降级），新片段有全新失败预算 |
| App 重启 / 崩溃 | 一期：暂停态丢失，显示为已中断（可接受）；二期换文件 store 后可续 |
| 暂停状态下点停止 | 现有停止语义 + 清掉这批子 agent 存档（明确丢弃，不留僵尸） |
| 暂停时用户插话（纠偏/提问） | 走现有插话通道：纠偏话记下来，随续跑一并带上 |
| 没有子 agent 在跑时点暂停 | 就是最普通的停止，只是文案叫暂停、自动可续 |

## 实施分期

- **一期（核心体验）**：暂停/停止分离（reason 标记 + 文案）、子 agent
  paused/resumed 卡片态、「继续」按钮 + 续跑注入、单飞保护。内存 store 够用。改动
  集中在：中断路径的 reason 传递、SubagentActivity 事件、`chat.ts` 的续跑入口。
- **二期（抗重启）**：GUI 的 `subagentStore`（现为 `chat.ts` 里的 `MemoryStateStore`）
  换成会话快照目录下的文件 store，重启后暂停的也能续。
- **三期（锦上添花，可不做）**：单卡暂停（只暂停某一个子 agent）、退出 App 时询问
  "有暂停中的任务"。

## 验收口径（一期）

1. 三个子 agent 并行跑时点暂停：LLM 流立即停，正在跑的工具收尾后存档，卡片全部变
   "已暂停"，输入框解锁。
2. 点「继续」：父回合续跑、重新委派，子 agent 输出接在断点之后（transcript 可见
   上文，不重做已完成步骤）。
3. 暂停后不发「继续」、直接开新任务：新任务正常跑，暂停卡片保持不动、不自动复活。
4. 暂停状态下点停止：停止语义照旧，存档清空。
5. 全量测试绿；新增用例覆盖 paused 事件、续跑注入、单飞置灰。

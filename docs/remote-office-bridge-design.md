## 0. 评审结论（一段话）

v1 桥接设计是**当前架构上的最优补丁，不是最优架构**：它在持久层用错了原语
（快照 + 追加账两种格式表达同一历史），在进程模型上选了双主（GUI 与网关各持
引擎、靠 sessionId 交接），由此派生出交接协议、宿主语义同步税、版本偏斜三类
本可不存在的问题。架构最优解是两根柱子：**A1 会话 = 只追加的事件日志（快照
降为压缩视图）；A2 引擎所有权收敛到无头宿主（daemon），GUI 与手机降为对称的
投影 + 输入面**。两根柱子都顺着仓库第一原则「事件即接口」——该原则今天在
持久层被违反（事件流落盘时被压扁成 messages 快照），本评审就是把原则补到
持久层和进程模型上。

产品需求不变（v1 §0 原文）：同一任务双向留痕互见；本地表现形式可小改不可
大改、尽可能不变、背后随便变。R1–R3 三条红线全部继承，且在单主架构下 R2
（对话流零扰动）与 R3（离场不依赖 GUI）从「靠协议保证」升级为「靠结构保证」。

## 1. v1 的架构级缺陷（为什么替换）

| # | 缺陷 | 机理 | v1 的处理 | 架构评审的裁决 |
|---|---|---|---|---|
| V1 | 持久原语错配 | session.json 是全量快照（整体重写、无增量语义），为此 v1 不得不加 mirror.jsonl 追加账——两种格式表达同一历史 | 双记账 + 单写者协议补救 | 原语换成事件日志，双记账与协议同时消失 |
| V2 | 双主共享状态 | GUI 开=webview 引擎跑、GUI 关=网关 node 引擎跑，sessionId 命中同一检查点做交接 | 所有权约定 + 「GUI 开着时单点写入」 | 单主消灭交接；两引擎并发（GUI 半开、手机在跑）在 v1 里无定义 |
| V3 | 宿主语义税 | 控制面（插话分类/steer/暂停宽限/起飞闸）焊死在 chat.ts，CLI 宿主没有——两宿主行为已经不同（评审 F1 实证） | M2.5 补 CLI steer 接线 | 税根是控制面位置，接线只是继续交税；抽出后一类问题不存在 |
| V4 | 版本偏斜 | GUI 与网关侧车可能不同代，checkpoint 语义漂移 | 「同包分发」一句带过 | 单主下只有一份引擎与控制面，偏斜不可能发生 |

v1 中**仍然成立并被继承**的部分：IM 作为手机中继（出站 WebSocket、零公网暴露
——本地优先产品的正确选择）；通道投影复用（桌面同款渲染管线截图给手机）；
绑定模型（channel peer ↔ session）。

## 2. A1 持久层：会话 = 事件日志

### 2.1 目标形态

```
~/.pure/sessions/<sessionId>/
  events.jsonl     唯一事实源：每行一个事件 {seq, ts, kind, actor, payload}
  snapshot.json    压缩视图：events 的定期 fold（快照 = 日志的物化，不是真相）
```

- **多写者安全**：事件是原子行追加（单行 ≤ 缓冲区、O_APPEND），多进程并发追加
  只交错过界、不互相覆盖——这是日志原语天然保证、快照永远给不了的。写者带
  actor 标注（gui / gateway / sleep-time），序号在读取侧归并排序。
- **事件 schema（草案，v1 版本化）**：复用既有事件词汇，不发明新体系——
  `EngineEvent`（THINK/ACT/ToolResult/Completed/Interrupted 的持久化形态）、
  `SubagentActivity`、`user_input`（带 origin: {surface, channel?, peer?}）、
  `insertion_classified`、`receipt`、`approval_request/decision`、
  `plan_updated`、`snapshot_saved`（fold 里程碑）。事件即接口原则的直接落盘。
- **压缩**：每 N 个事件或回合收尾做一次 fold 产出 snapshot.json（= 现在的
  快照语义），重启恢复 = 读 snapshot + 重放其后增量。FSStore 检查点体系是
  fold 的特例（引擎断点），不变。

### 2.2 消费者全部变投影

| 消费者 | v1 机制 | A1 机制 |
|---|---|---|
| GUI 转录 | session.json 快照直读 | 日志 tail 投影（实时渲染 = 重载渲染由同源保证） |
| 手机 digest | mirror 账 + 档案 tail 轮询 | 日志 tail + 网关 WS nudge（只带 sessionId 不带内容） |
| 断点续跑 | FSStore 检查点 | snapshot fold + 增量重放（检查点体系不变） |
| 远端镜像记录 | mirror.jsonl | 就是日志本身（user_input 带origin） |
| 回放/收割/审计 | session.json messages 解析 | 日志过滤投影（信息严格更多：分类、回执、时序都在） |

一个原语消灭四种专用机制；现有 session.json 消费者（收割器、历史会话还原、
睡眠编排器）经「日志→messages 投影」兼容层逐个迁移。

## 3. A2 进程模型：单主宿主

### 3.1 关键事实与卡点

- **引擎已是宿主无关的**：CLI harness 在 node 进程跑同一份 AgentLoopEngine/
  编排器/Harness——这不是设想，是既有事实（通道会话今天就这么跑）。
- **卡点是控制面**：插话分类、steer 队列、暂停宽限、起飞闸、计划卡驱动全部
  焊死在 chat.ts（GUI 专属）；这既是 V3 语义税的根，也是「同一任务多表面」
  必须靠交接的原因。**控制面抽出 = self-evolution-welding-plan 的 P3-2 刀 +
  蓝图第 8 期，路线图早已指向这里。**
  （✅ 2026-10-08 此卡点已解除：五刀收官，插话分类、steer、暂停宽限、折入闸、
  起飞闸、回合收尾序全部住进宿主无关模块，chat.ts 退为投影与组装；计划卡驱动
  按裁决留宿主——纯 GUI 投影，S3 搬运清单含 AutoContinueScheduler。）

### 3.2 目标形态

```
本地 daemon（网关进程即其胚胎；引擎 + 控制面 + 事件日志的唯一写者）
 ├─ GUI      = 投影 + 输入面（订阅日志，写 user_input/steer/approval 事件）
 ├─ 手机通道 = 投影 + 输入面（网关原生就在：IM ↔ 事件读写）
 └─ webchat  = 投影 + 输入面（现有 WS 直接升级为日志订阅）
```

- 输入即事件：用户消息、插话、批准、暂停/继续，从任何表面来都是往日志写
  一条带 origin 的事件；控制面（单份）消费日志驱动引擎。五分类只有一份、
  跑在 daemon 侧——GUI/CLI 语义漂移不可能发生。
- GUI 开/关只是「有没有一个观察窗在场」：出游场景 = 手机是唯一窗；回家 =
  GUI 打开即从日志恢复到同一现场（R3 结构性成立，无交接协议）。
- 插话协议（蓝图第 1–2 期）在 daemon 侧对通道来源同权：手机的话进同一分类
  器，点名停支/前提止损对远端输入一视同仁（R2 结构性成立）。

### 3.3 被结构消灭的问题清单

双主交接协议、session.json 所有权、宿主语义审计、GUI 半开时的并发引擎、
GUI/侧车版本偏斜、mirror 双记账——六项在 A1+A2 下**不存在**，不是被规避。

## 4. 绞杀者迁移序（每步独立可发布、可回退）

| 步 | 内容 | 独立价值 | 回退性 |
|---|---|---|---|
| S1 | 事件日志地基：events.jsonl 落盘（引擎事件流 + origin 输入事件）+ 兼容投影层喂现有消费者；快照变 fold | 双宿主世界立即受益：同步 = 读日志，漂移审计有据 | 纯增量，旧快照路径保留 |
| S2 | ✅ 已收官（2026-10-08，五刀）：插话分类、steer、暂停宽限迁出 chat.ts 成宿主无关模块，GUI/CLI 同接；CLI 真缝 delegation/roundClose/steerRunningTurn，插话输入路落地时一次接上 | CLI 语义补齐、chat.ts 减重、双宿主税减半 | 模块化搬家，行为回归锁 |
| S3 | daemon 化（分水岭，可缓行）：网关进程持有引擎与控制面，GUI 改订阅 + 输入；本机日常使用也走 daemon | 远程办公全套自然掉出；后台执行/多窗免费获得 | 最大的一步；S1/S2 不做它也已完成全部结构收益 |

**S1 无论终局如何都值得**：它是远程办公的地基、防缠原则在持久层的补课、
S3 的前置——三重收益、零赌注。S3 是明确的分水岭决策：不 daemon 化也已完成
结构性修复（V1/V3/V4 消除），只是保留 V2（双主）以「同版本约束 + 日志对账」
低成本维持。

## 5. 代价与反方观点（照实记）

- **日志写放大与增长**：事件粒度落盘比快照频；缓解 = 事件体有界（工具结果
  40K 截断既有）+ fold 压缩 + 每会话单文件。量级：与现快照同数量级。
- **GUI 对 daemon 的运行时依赖**：S3 后本机使用也要求 daemon 在跑（今天 GUI
  独立可用）。缓解：随 app 自启（托盘常驻），崩溃自动重启——但这是真实的
  新依赖，S3 拍板时按此计价。
- **迁移成本**：S1 是持久层重写（消费者逐个过兼容层）；S2 是 chat.ts 大刀
  （P3-2 早有此账）；S3 是进程模型搬家。三步合计显著大于 v1 桥接的 M0–M3，
  换的是永久不再交 V1–V4 的税。
- **「本地零改动」红线的边界**：R1/R2/R3 在 S1/S2 阶段零风险（纯幕后）；
  S3 阶段 GUI 流式改经 WS（毫秒级，webchat 已证明），渲染层仍零改动。

## 6. 验收判例（继承 v1 §6，语义不变）

1. 本地启动任务 → 关电脑 → 手机问答/批准/停支（停支在 S2 后生效，S1 阶段
   为问答 + 批准）→ 回家 GUI 重开，全部互见。
2. 两边同场：手机插话按五分类处理，不打断、不重排、不新开形态。
3. 未绑定/未订阅的会话与通道行为与今天逐字节一致（回归红线）。
4. 新增：拔掉 daemon（S3 后），GUI 降级提示而非假死；日志与快照对账一致。

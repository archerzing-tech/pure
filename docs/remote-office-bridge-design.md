# 远程办公 L2：会话桥——同一任务的双向同步记录

状态：**方案定稿（2026-10-01，用户需求原文定调），未实施**。上游：对话智能
升格蓝图（第 1–3 期是其地基）、channel-gateway-design.md、cn-im-channels.md。

## 0. 需求原文与硬红线

> 两条通讯的路（本地 GUI + 手机通道）如果操作的是同一个任务，要彼此都留有
> 记录，信息是同步的：手机端可以看到本地端操作的信息，本地端也能看到手机端
> 操作的信息。**当前本地端的表现形式我很满意，不要影响了当前的表现形式和
> 对话形式。**
>
> v2（2026-10-01 用户放宽定调）：表现形式**可以有小改动，但不能大改，
> 尽可能不变；背后怎么变是可以的**。

红线拆成三条可验收的约束（按 v2 口径校准）：

- **R1 渲染小改不大改**：chat.ts 现有的消息流、卡片、插话回执、暂停/继续条
  的形态不动。允许的"小改"限定为：既有元素上加徽章/角标（如 📱 来源标），
  不新增会话形态、不重排既有消息的渲染路径。**架构原则照旧：改动落在消息
  数据形状（origin 标注）上，渲染层只做最小认领——背后（同步机制、进程
  模型、存储）随便变。**
- **R2 对话流零扰动**：本地正在跑的回合不会被远端事件打断或重排；手机的话
  走既有插话管线（五分类），分类结果决定它排队/折入/点名——不是新通路。
- **R3 离场不依赖 GUI 活着**：GUI 关掉后手机仍能继续同一任务；GUI 重开后，
  手机干过的一切以记录形态在场（不是"错过"）。

## 1. 现状三事实（代码证据，设计建立在这上面）

| # | 事实 | 证据 | 后果 |
|---|---|---|---|
| F1 | 通道会话只落引擎检查点，不落转录档案 | `~/.pure/sessions/chan_*/` = `checkpoints/` + `meta.json`，无 `session.json` | 手机侧的操作今天没有"可被本地看见"的记录形态 |
| F2 | GUI 的子代理检查点是内存态 | `chat.ts:1621 MemoryStateStore`（蓝图第 3 期既知缺口） | GUI 重开后续跑只靠转录恢复；与通道侧 FSStore 不同种 |
| F3 | 通道路由键 = (channel, peer) → workspace，会话 id 现生成 | `router.ts:100` `chan_<ts>_<rand>` | 没有"这个手机对端绑定到 GUI 会话 X"的概念 |

## 2. 总设计：同一任务 = 同一份会话档案

不引入"任务"这个新实体——**绑定的 GUI 会话档案就是唯一事实源**：

```
~/.pure/sessions/<sessionId>/          ← 绑定后，两侧共同读写这一份
  session.json      转录（镜像条目见 §3）
  checkpoints/      引擎检查点（FSStore；两侧同参续跑命中同一存档）
  mirror.jsonl      远端事件账（手机入站消息 + 网关回执 + 投递状态）
  meta.json         绑定关系（channel, peer, accountId, workspace）
```

- **绑定**（一次性动作，GUI 设置或会话内一句「把这个会话接到手机」）：
  在 channels.json 的 `bindings` 里给该 (channel, peer) 增加一条
  `sessionRef: <sessionId>`；网关 PairingGate 完成配对即绑定生效。
- **手机 → 本地**：网关收到绑定对端的消息后，除了走会话逻辑，**同刻**把
  `{原话, 分类, 回执, 时刻}` 追加进 `mirror.jsonl` 并把用户气泡/回执写进
  `session.json` 转录（镜像条目，§3）。本地端无论在场与否都"看得见"。
- **本地 → 手机**：本地回合的收尾/交付（Completed 事件的 final 输出、计划卡
  变更、暂停/继续）由既有快照保存路径**顺带**追加到 session.json + mirror 账；
  网关侧对绑定会话做档案 tail（节流），有新 final 就走既有通道投影管线
  （markdown → 同渲染截图）推给手机。**不新增投影代码，只新增 tail 触发**。

## 3. 镜像条目：R1/R2 的结构性保证

手机的操作在本地转录里是**新消息形状**，不是新界面：

- `Message` 增一个可选 `origin?: { channel: string; peer: string; at: number }`
  标注（缺省 = 本地，**既有消息逐字节不变**）。转录投影
  （transcriptProjection）认它：手机来的用户气泡带一枚「📱 手机」来源徽章，
  网关回执按现有回执气泡渲染——**渲染词汇全部来自现有 UI 件**，零新形态。
- 重放/存档语义与既有插话消息同规：`origin` 随档案持久化，重载渲染 = 实时
  渲染（蓝图跨期纪律「实时 = 重载」直接继承）。
- 本地正在流式时手机来话：网关不直接写转录（避免与活写入竞争），先进
  mirror 账 + 由 GUI 的既有插话通道注入活会话（§4 形态 C）；回合收尾的
  快照保存点把 mirror 账里未入档的条目并入 session.json——**写入仍单点在
  GUI 的保存路径**，R2 因此是结构保证而不是约定。

## 4. 三个运行形态（数据流各一条）

**A. 只本地（现状，零变化）**：手机不说话，一切照旧——桥是惰性的，绑不绑定
都不产生任何本地可见差异（红线回归测试锁"未绑定时逐字节一致"）。

**B. 只手机（GUI 关闭/出游中）**：网关用**绑定会话的 sessionId** 起 CLI
harness（createCliChannelHarnessFactory 现成），FSStore 检查点命中本地留下的
断点 ⇒ 手机从本地停下的地方继续。手机侧消息与 pure 的回执、产出，由网关写
mirror 账 + session.json 转录。GUI 重开 → loadSession 恢复同一档案 →
镜像条目让"手机干过什么"完整在场（R3）。

**C. 都在场（最微妙，也最被 R2 约束）**：本地正在跑，手机来话——
  1. 网关把消息交给**绑定会话的插话通道**（不是另起会话）：GUI 侧把网关
     的入站当作一条来自 `origin` 标注来源的用户插话，喂给**现有**
     DynamicInsertionCoordinator——五分类决定它 question 旁答 / steer 折入 /
     点名某支 / task 排队。回执走现有回执管线，同时抄送 mirror 账 →
     网关 tail 到回执 → 手机收到（插话协议的「话到即达」对通道来源同权）。
  2. 手机上要做**新决策**（批准权限卡）：网关的审批 broker 走现有
     approval 通道卡（QQ/飞书文字双轨已实现），批准结果同样进 mirror 账。
  3. 本地的进度对手机：不必逐帧——回合收尾 + 计划/暂停/继续等关键节点经
     通道投影推 digest（投影管线现成，只加触发）。

## 6. 验收判例（用户场景直译）

1. 本地启动调研任务 → 关电脑出门 → 手机（QQ/飞书）问「现在到哪了」→ 得到
   旁答 + digest；说「停掉 jev 那支」→ 那支真停、其余照跑（分支中止对通道
   来源同权）。
2. 回家打开 GUI → 该会话恢复，转录里手机的每句话（📱 徽章）、每条回执、
   手机驱动的每个动作都在场；本地继续说一句话，对话形态与今天完全一样。
3. 两边同时说话：本地在跑，手机插话 → 本地按五分类处理（旁答/折入/点名），
   **不打断、不重排、不新开形态**；手机收到对应回执。
4. 未绑定的会话与通道行为与今天**逐字节一致**（红线回归）。

## 7. 明确不做

- 不做「两端实时同屏」：镜像的粒度是**记录与关键节点**，不是逐 token 流
  （投影 digest 已够手机用；逐帧同步是带宽与复杂度黑洞，收益不成比例）。
- 不做手机侧完整 GUI：手机的操作面 = 说话 + 批准 + 看摘要（通道已有的面）。
- 不改 chat.ts 既有渲染与对话流（R1/R2）；所有新能力以 origin 标注、mirror
  账、tail 触发三件增量落在既有接缝上。
- 不新建跨进程消息总线：同步介质就是会话档案（产物唯一形态原则——档案即
  接口），网关与 GUI 之间零直连、零新协议。

# 阶段 13：能力自扩展——工具与子 Agent 的生成与优化

状态：**方案定稿（2026-09-20），未实施**。起因：用户问系统能否自己生成新工具、
改进存量工具、生成新子 agent、改进存量子 agent。审计结论：四项里两项不具备、
两项只有半个（见下）。本设计补齐，同时守住既有三条纪律。

## 现状审计（2026-09-20，按代码说话）

| 能力 | 现状 | 证据 |
|---|---|---|
| 生成新工具 | ❌ | 工具面 = `BUILT_IN_TOOL_DEFS`（toolDefs.ts）+ ToolRegistry 权限表，编译期防呆（新工具不配权限映射直接编译错误）；唯一动态通路是 MCP（挂外部的，不是自己长的） |
| 改进存量工具 | ⚠️ 半个 | E1.3 工具修正建议：错误聚簇 → 使用注意进记忆 + 建议卡。进化的是"怎么用"，工具本体与描述没有回路去改 |
| 生成新子 agent | ❌ | 名册硬编码（`BUILT_IN_SUBAGENTS` SubagentOrchestrator.ts:658 + `CODING_AGENT_ROLES` :723）；E1.4 设计原话"只建议，绝不自动改配置" |
| 改进存量子 agent | ⚠️ 半个 | persona 文本固定；在变的是工作环境（反思器 lesson/procedure 注 prompt、E4.1 记结局、E1.4 出卡）。角色行为随记忆漂移，prompt 本体无人改 |

**可复用的存量接缝**（设计建立在这上面，不另起炉灶）：

- `DefaultSubagentRegistry.register()` 是运行时 Map——差的不是基础设施，是谁来回调；
- MCP 的 `onToolDiscovered → toolRegistry.register()` 已证明动态注册通路可行；
- SKILL.md 机制已证明"运行时加载文件 → 改变行为"可行（E2.2 甚至能自己写 SKILL.md）；
- E4.1 派发结局观测 + E1.3/E1.4 建议卡已有数据源和展示位。

## 设计立场

1. **度量准入**（纪律 1 的延伸）：每个自动生成物必须有评测或真实使用数据支撑才能
   转正；没有尺子的能力不上线。生成便宜，准入严格。
2. **用户可见可控**（纪律 3）：一切生成物落盘（`~/.pure/` 下各自目录），可看、可删、
   可导出；删除文件即完全回滚；设置里一个总开关。
3. **不新建安全面**（2026-09-17 优先级）：生成工具的执行复用现有 execute_command
   信任模型与超时/取消体系；权限标注按操作类型自动打标，与手写工具走同一套确认门。
   不新建沙箱，不新增确认步骤。
4. **用户触发优先，自动识别为辅**（E2.2 立场）：第一版生成动作都由用户一句话触发
   （"造一个专管 X 的子 agent"、"把这个脚本固化成工具"）；自动识别只负责"建议你
   可以生成"，不自己动手。

## 分期机制

### 13.1 建议一键应用（E1.3 / E1.4 收尾）

现状止步于"告诉你拉哪个闸"。改：建议卡加「应用」动作——
E1.4 的 skill-gate 类直接写技能开关；E1.3 的工具注意直接落记忆（`tool:` 前缀注入
机制已有）。每次应用记一条观测，回看"应用了的建议后来有没有效果"，把建议层也
接进度量闭环。改动面：optimizeCard / 进化设置页 + i18n。**零新风险面。**

### 13.2 子 Agent 生成

流程：用户一句话（或 E4.1 识别出"同类任务被反复手工拆解"→ 建议固化）→ 模型起草
`SubagentDefinition`（name / description / input_schema / createSystemPrompt /
预算 / 超时）→ 校验（schema 合法、名字不与内建/MCP 冲突、预算封顶）→ **试用制
准入**：新角色先以"试用"状态注册（卡片带试用角标），接 5–10 个真实委派，结局
数据 ≥ 同类现有角色基线才转正；不达标自动归档并出卡说明。

落盘：`~/.pure/subagents/<name>.json`，启动扫描 → `register()`。删除文件即消失。

### 13.3 存量子 Agent prompt 自改进

persona 拆两层：代码里的 base（不动）+ 进化 overlay（`~/.pure/personas/<role>.overlay.md`），
`createSystemPrompt` 时合并。回路：E4.1 结局数据显示某角色持续短板 → 反思器起草
overlay（只增补约束/技巧，不重写 base）→ **准入门槛**：该角色的回归小套件（从历史
真实派发抽 5–10 例）A/B，overlay 版不输 base 版才落盘。删 overlay 文件即回原样；
仪表盘标出哪些角色带 overlay。

#### 13.3 part 3 起草流 —— 实现机制（2026-09-22 补充）

part 1（装载合并 `47cb2da`）与 part 2（回归 A/B 门槛 `b4abd2b`）已落地，本段是把
两者接成闭环的机制：

1. **触发**：`scanSubagentAdvice`（E1.4，已有）在窗口内发现某角色"派发够多、失败
   够密" → 出建议卡。起草流不另设发现逻辑。
2. **起草**：新增 `PersonaOverlayReflector`，复用 E1.1 `LessonReflector` 的便宜模型
   往返模式——输入该角色的失败画像（dominantKind / timeoutCount / avgDurationMs /
   失败样本）与 base persona 摘要，输出一段 ≤ `MAX_OVERLAY_CHARS` 的 overlay 文本。
   防幻觉纪律同 E1.1：只准引用证据目录里的调用哈希，编造的 id 一律剥掉。
3. **校验**：草稿必须过 part 1 的同一编译器 `compilePersonaOverlays`（role 名合法 /
   ≥8 字符 / ≤4000 / 角色存在）才许进入下一关——与 13.2 生成半边"草稿必须过 S2 同一
   校验器"同一条纪律。
4. **准入**：该角色回归小套件跑 base vs base+overlay，`roleRegressionVerdict` 裁决；
   DENY（样本不足）/ REJECT（回归）→ 草稿不落盘，回执说明原因；ALLOW → 落盘前确认
   弹窗 + 同名文件不覆盖（比照 13.2 三道门）。
5. **标记**：`list_persona_overlays`（Rust，part 1 已有）→ E4.1 角色切片表加「overlay」
   徽章（有/无）。删文件即回滚，徽章自然消失。

**关键依赖（顺序）**：准入要求 ≥ `MIN_ROLE_CASES`=5 例真实样本，而当前
`evals/roles/` 是 3 个手写种子、刻意不达标 → **落盘路径在真实样本到位前始终是 DENY**。
所以样本来源必须先于起草流的落盘落地。

**样本来源（2026-09-22 核实，含一处文档修正）**：

- `evals/roles/README.md` 原话"真实样本来自 E4.1 outcome 数据里该角色的委派 args"
  **不成立**——`AgentRunObservation.toolCalls` 的 `ToolObservation` 只记
  `toolName / success / durationMs / result(哈希) / error`，**不存 args 也不存产出文本**
  （E0.1 设计明写"不存任何 prompt 文本"）。
- 真实样本可回收的地方是**会话存档**：`~/.pure/sessions/<id>/checkpoints/*.json` 的
  `state.messages` 含 assistant toolCall 的 `function.arguments`（= 委派 args）与其配对
  的 tool result（= 子 agent 产出）。Harvester 从这里抽 `{role, args, output}`。
- **待拍板**：真实产出不能自动变成"该出现什么"（内容断言 must/mustNot）。两条候选
  路——(a) reflector 用一次便宜模型从（base 产出 + 角色契约）起草断言，断言只在
  base 侧通过时才收录（自洽门）；(b) 只自动收割 `{args, output}` 候选，人工从清单里
  挑并写断言。

### 13.4 工具生成

形态：脚本工具包 = `~/.pure/tools/<name>/` 一目录，`TOOL.json`（name / description /
input_schema / exec）+ 实现脚本。启动扫描 → 构造 TaggedTool → `toolRegistry.register()`
（MCP 同款通路）。

流程：模型在对话里写的脚本在过程记忆（procedure）里复用 ≥ 2 次 → 提示"固化成
工具？"（用户点头才动手）→ 起草 TOOL.json + 脚本 → **试跑**（按 input_schema 造
样例参数跑一遍，成功才算起草完成）→ 注册。执行复用 execute_command 语义；权限按
操作自动打标，与手写工具同一套门。

## 边界情况

| 情形 | 行为 |
|---|---|
| 生成的名字与内建 / MCP / 既有产物冲突 | 拒绝注册，出卡说明；内建名永久保留字 |
| 生成的工具 / 角色连续失败 | 自动停用（隔离，不删除）+ 出卡；用户可看可删可重新启用 |
| 试用角色数据不足（委派次数不够） | 保持试用态，不强行判定；用户可手动转正 |
| overlay 把角色越改越差 | A/B 门槛挡在落盘前；落盘后仪表盘可对比，删文件即回滚 |
| 会话中生成物被引用但文件已被删 | 注册表启动时扫描，运行中不热删——下个会话自然消失 |
| 生成请求本身写坏了 JSON / schema | 起草阶段校验拒绝，原样退回给模型重写（同 parseToolArguments 的修复思路） |
| 用户关闭总开关 | 所有生成物不加载、建议卡不再出、已有产物保留在盘上 |

## 实施顺序与理由

1. **13.1 先行**：零风险收尾，顺手把建议层接进度量闭环——后面三期的"准入数据"
   都靠这个闭环攒。
2. **13.2 次之**：接缝全现成、产物是纯文本、试用制简单；是"生成"价值最高的一步。
3. **13.3 跟上**：依赖 13.1/13.2 攒的观测与评测习惯（角色级回归集是新基建，是本
   期主要工作量）。
4. **13.4 最后**：通路无悬念（MCP 已证明），但试跑与固化流程最繁琐；在阶段 10
   （沙箱）有结论前保持"用户触发生成、不自动触发"。

## 验收口径

1. 13.1：建议卡一键应用后设置 / 记忆确实变更；应用记录进观测，仪表盘可回看效果。
2. 13.2：生成的角色可被正常委派，试用角标 / 数据可见，不达标自动归档，删文件即消失。
3. 13.3：overlay 仅在有 A/B 数据支撑时落盘；删文件即回滚；角色回归集不倒退。
4. 13.4：生成的工具出现在工具列表、可调用；试跑通过才注册；连续失败自动停用出卡。
5. 全程：总开关关掉后行为与现状逐字节一致；全量测试绿。
